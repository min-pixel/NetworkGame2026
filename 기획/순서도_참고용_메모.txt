1. 이벤트 큐를 쓰는 이유

이벤트 큐란
클라의 TCP 수신 스레드가 받은 패킷(접속 결과, 로비 상태, 게임 시작, 사망, 결과)을 쪽지처럼 넣어 두는 상자예요. 클라의 메인 스레드는 매 프레임 이 상자를 열어서 쪽지를 꺼내 처리해요.

안 쓰면 생기는 문제

서버의 게임 루프 스레드가 “B 사망” 패킷을 보내요.
클라A의 TCP 수신 스레드가 받자마자 직접 탱크 목록에서 B를 지워요.
바로 그 순간 클라A의 메인 스레드는 같은 탱크 목록을 돌면서 탱크를 그리고 있었어요.
메인 스레드가 방금 지워진 B를 그리려다가 프로그램이 튕겨요.

쓰면

클라A의 TCP 수신 스레드는 “B 사망” 쪽지를 큐에 넣기만 해요.
클라A의 메인 스레드가 그리기 전에 쪽지를 꺼내서 직접 B를 지워요.
지우기와 그리기를 같은 스레드가 차례대로 하니까 부딪칠 일이 없어요.

덧붙여

큐 자체는 두 스레드가 같이 만지니까 큐 임계 영역으로 지켜요. 메인 스레드는 임계 영역 안에서 큐를 통째로 바꿔치기(swap)해서 꺼내고 바로 나와요.
TCP는 보낸 순서대로 도착하고, 큐도 넣은 순서대로 꺼내져요. 그래서 큐는 순서를 맞추려고 쓰는 게 아니에요. 스레드끼리 부딪치지 않게 하려고 쓰는 거예요.

2. 늦게 온 건 버림 / 다시 입력 받기 / 마지막 입력 / 최신 것으로 덮기

① 늦게 온 건 버림 (서버의 UDP 수신 스레드, 클라의 UDP 수신 스레드)

UDP는 보낸 순서와 다르게 도착할 수 있어요.

입력 예시:

클라A의 메인 스레드가 입력 10번(W 누름)을 보내고, 바로 다음 프레임에 11번(W 뗌)을 보내요.
서버의 UDP 수신 스레드에 11번이 먼저 도착하고, 10번이 나중에 도착해요.
10번을 그대로 쓰면, 이미 손을 뗐는데 W를 누른 걸로 바뀌어서 기체가 앞으로 가요.
그래서 "마지막으로 받은 11번보다 작은 10번은 늦게 온 것"으로 보고 버려요.

상태 예시도 같아요. 클라A의 UDP 수신 스레드에 200틱 상태가 오고 뒤늦게 199틱 상태가 오면, 199틱을 쓰는 순간 기체가 뒤로 순간이동해요. 그래서 버려요.

② 마지막 입력 (+ UDP 주소, 4명분) (서버)

플레이어마다 가장 최근 입력 하나만 넣어 두는 칸이에요. 서버의 게임 루프 스레드는 틱마다 이 칸을 복사해 가서 써요.
큐처럼 쌓지 않는 이유가 있어요. 입력은 "지금 W를 누르고 있나" 같은 지금 상태라서 최신 하나면 충분해요. 쌓아 두면 옛날 입력부터 처리하느라 조작이 점점 밀려요.
같은 칸에 그 클라의 UDP 주소도 저장해요. 게임 루프 스레드가 상태를 보낼 때 이 주소로 sendto해요.

③ 다시 입력 받기 (서버의 UDP 수신 스레드)

입력을 칸에 저장한 뒤 다시 recvfrom()으로 돌아가서 다음 패킷을 기다린다는 뜻이에요.
이 스레드는 받기 → 검사 → 저장을 서버가 꺼질 때까지 반복해요. 순서도의 되돌아가는 화살표가 이거예요.

④ 최신 것으로 덮기 (클라의 UDP 수신 스레드)

서버와 똑같은 방식의 클라 쪽 버전이에요.
상태 패킷을 받으면 이전 것을 지우고 새 것으로 덮어써요. 클라의 메인 스레드는 매 프레임 가장 최근 것만 읽어서 화면에 반영해요.

②와 ④에도 임계 영역이 필요한 이유

클라의 상태 칸: 클라A의 UDP 수신 스레드가 새 위치를 반쯤 쓴 순간(x만 새 값, y·z는 옛 값)에 메인 스레드가 읽으면, 기체가 엉뚱한 곳에 한 프레임 그려져요.
서버의 입력 칸: 서버의 UDP 수신 스레드가 클라B의 입력을 쓰는 도중에 게임 루프 스레드가 복사하면, 이동은 새 값이고 발사는 옛 값인 섞인 입력이 돼요.
그래서 쓰는 쪽도 읽는 쪽도 임계 영역 안에서 복사만 하고 바로 나와요.

3. 송신 임계 영역을 쓰는 이유

전화선으로 생각하면
서버에는 클라마다 TCP 소켓이 하나씩 있어요. 클라1과 연결된 전화선이 하나 있다고 생각하면 돼요. 이 전화선으로 클라1에게 말할 수 있는 서버 스레드는 여럿이에요.

서버의 클라1 TCP 통신 스레드: 클라1의 접속 결과
서버의 클라2 TCP 통신 스레드: 클라2가 준비하면 로비 상태를 전원에게, 그러니 클라1에게도
서버의 게임 루프 스레드: 게임 시작 패킷을 전원에게

안 지키면 생기는 문제
send()는 한 번에 다 못 보내고 일부만 보낼 때가 있어서, 남은 부분을 반복해서 보내야 해요.

로비에서 클라2가 준비해요. 서버의 클라2 TCP 통신 스레드가 클라1에게 로비 상태(12바이트)를 보내다가, 앞의 5바이트만 나갔어요.
바로 그때 클라3이 접속해요. 서버의 클라3 TCP 통신 스레드도 클라1에게 로비 상태를 보내요.
클라1의 TCP 수신 스레드가 받는 바이트는 "첫 패킷 앞 5 + 둘째 패킷 12 + 첫 패킷 뒤 7"이에요.
헤더의 size대로 자르면 엉터리 패킷이 되고, 그 뒤로는 모든 패킷의 경계가 어긋나요. 접속이 끝날 때까지 되돌릴 수 없어요.

해결: 전화선마다 "사용 중" 팻말

클라마다 송신 임계 영역을 하나씩 둬요. 이게 "사용 중" 팻말이에요.
모든 TCP 전송은 SendPacket(클라 자리, 데이터, 길이) 함수 하나로만 해요. 이 함수는 받을 클라의 팻말을 걸고, 다 보낸 뒤 내려요.
그 사이에 다른 스레드가 같은 클라에게 보내려고 하면, 팻말이 내려질 때까지 기다려요.
클라3에게 보낼 때는 클라3의 팻말만 걸어요. 클라1에게 보내는 스레드와는 서로 기다리지 않아요.
함수를 클라마다 4개 만드는 게 아니에요. 함수는 하나이고, 팻말(임계 영역)이 클라 자리마다 하나씩 들어 있어요.

임계 영역이 못 하는 것: 순서

임계 영역은 "동시에 보내지 않게"만 해 줘요. "누가 먼저 보내나"는 정해 주지 않아요.
"로비 상태 다음에 게임 시작"이라는 순서는 다른 것이 지켜요. 서버의 TCP 통신 스레드가 로비 상태를 다 보낸 뒤에 SetEvent()로 게임 루프를 깨우는 코드 순서예요.

순서도에서 표시한 곳

결과·로비 상태 전송
로비 상태 알리기
게임 준비의 시작 패킷

이 세 곳은 여러 스레드가 같은 클라에게 동시에 보낼 수 있어요. "로비로 되돌리기"는 그 순간 TCP 통신 스레드들이 모두 기다리는 중이라 표시를 뺐어요. 그래도 SendPacket()을 거치니 자동으로 지켜져요.
